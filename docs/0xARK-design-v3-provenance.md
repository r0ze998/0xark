# 0xARK 設計ノート v3 — 来歴中心設計（Provenance-Driven Design）

最終更新: 2026-06-XX（セッション継続）
位置づけ: v2ノート（ネットワーク効果への転換）を、具体的なメカニクスまで落とし込んだもの。
v1 の崩壊リスク（デフレ・新規枯渇・賭博性）を「来歴（provenance）を中心に据える」ことで
裏返す設計。**進化メカニクスは実装可能段階**。steal 本体・トークン詳細はまだ残論点あり（§6）。

---

## 1. 背骨: 来歴（provenance）がネットワーク効果の核

3AIレビュー（v2）で「人が増えるほど面白い on-chain ゲームがヒットする」を設計軸に据えた。
0xARK の他ゲームにない武器は **来歴** — カードがオンチェーンで「誰と戦い、誰から奪い、
何勝したか」の歴史を不可逆に刻むこと。これはブロックチェーンでしか作れない。

そして **steal（奪い合い）は来歴を生むエンジン**。同じ機能が、設計次第で:
- ゼロサムの暴力（v1）→ 敗者が消える → 負のネットワーク効果
- **来歴を生む全員参加の生産活動**（v3）→ みんな参加したがる → 正のネットワーク効果

問いは「steal するか否か」でなく「steal を来歴生産活動として設計するには」。

## 2. 中心メカニクス: tx 来歴でしかアンロックできない単体昇格進化

### 確定した設計
- **単体昇格方式**（合成でなく、1枚のカードが育って昇格する）。
  - 同じカードが Common→Uncommon→Rare→Legendary と姿を変え、**戦歴・奪取記録をそのまま受け継ぐ**。
  - RPG のキャラ育成型。「俺のこの相棒を育て上げる」物語。歴史が連続する＝来歴進化と完全一致。
  - 合成（2枚burn）は歴史を切るので不採用。供給 sink は別手段（ショップ/昇格コスト）で補う。
- **来歴階層 = レアリティ階層**（card_data の既存60枚構造にそのまま対応）:
  - 60枚 = 6ファクション × 10枚。各ファクション: Common 5 / Uncommon 3 / Rare 1（パッシブ持ち）/ Legendary 1。
  - 昇格ほど深い来歴を要求する。**上位ほど金で買えず、歴史でしかアンロックできない**＝Pay-to-Win 構造を破壊。

### 昇格条件（来歴ゲート、たたき台）
既存 `CardBattleHistory` のフィールドをそのままゲートに使う（**新規ストレージ不要**）:
| 昇格 | 来歴ゲート（例） | 使うフィールド |
|---|---|---|
| Common→Uncommon | 通算 wins ≥ 10 | `wins`（evolve で既に cumulative_wins 計算済み） |
| Uncommon→Rare | wins ≥ 25 かつ（legendary_kills ≥ 1 または owners_dropped_count ≥ 1） | `wins` / `legendary_kills` / `owners_dropped_count` |
| Rare→Legendary | wins ≥ 50 かつ acquisition_source == duel_won かつ kos ≥ N | `wins` / `acquisition_source` / `kos` |
※ 数値は要バランス調整（§6）。

### 昇格コスト
- 来歴（戦えば貯まる＝枯渇しない）+ **トークン消費**（sink）。
- 「無限に全部昇格」を防ぎリソース配分の判断を生む。3AI が指摘した「sink 頭打ち」を、
  罰でなく成長として解決（戦い続けないと上に行けない＝恒常プレイ動機＝人口維持）。

### 実装の足場（既存資産が揃っている）
- `CardBattleHistory` に wins/losses/kos/legendary_kills/owners_history/owners_dropped_count/
  acquisition_source/is_evolved/lease_* が **既に存在**。来歴記録のインフラは実装済み。
- `evolve_cards` は既に親の wins を読んで cumulative_wins を計算している（条件化していないだけ）。
  → 昇格ゲートは `require!` を足す形で組み込める。
- 技術方式は **単体昇格＝同一 mint のメタデータ更新**（mint address を変えずレアリティ/ステータス
  上書き → card_mint が変わらないので CardBattleHistory もそのまま連続）を軸に検討。
  Solana の NFT メタデータ更新制約は実装時に確認（代替: burn&mint + 履歴コピー継承）。

## 3. 縦横バランス: 育成（縦）と60枚コレクション（横）は食い合わない

**使用制限ルールは不要**（damage_calc が既に総力戦を強制しているため）:
- `judge_winner` は **5枚の bp 合計**で勝敗判定（1枚の傑出では勝てない）。
- 勝敗前にパッシブ（KnightAura=他Knight+1BP、EngineerOverclock=Engineer3枚で+2BP、
  MerchantGoldAura=Legendary居れば全体+1BP 等）とスロット相互作用（同スロット-3HP、
  UseFlame隣接-5HP 等）が走る → **複数枚の組み合わせ・配置**が効く。

結果、追加ルールなしで縦横が両立する:
```
横(コレクション) = 5枚の総合力 + ファクションシナジー + スロット配置の選択肢
縦(単体昇格)     = 個々のカードを強くする
両立 = damage_calc が「5枚全部の質」を見る → 育成と収集が自然に噛み合い、両方やった人が最強
```
（5ラウンド各ラウンド5枚出す前提なので「育てた1枚だけで戦う」はルール上そもそも不可能。）

## 5. 経済の全体像（v2 方向 + v3 具体化）

```
faucet IN                          sink OUT
 ・市場売買での稼ぎ(換金は売買で、賭けでない／CryptoKitties方式)
 ・シーズン順位報酬(既存 prize_pool, 限定)   ・ショップでベースカード購入
                                            ・昇格(進化)のトークンコスト ← v3 で恒常 sink に
                                            ・imprint 強化
 ※ トークン ante / 運営 rake は撤廃(賭博・デフレの主因)
来歴が市場価値に直結: 「あと N 勝で Legendary 化できるカード」が高く売れる
```
- トークン ante 撤廃 → 賭博リスク激減。稼ぎは市場売買へ。
- 昇格コストが「戦い続けないと上に行けない」恒常 sink になり、3AI の頭打ち批判を解消。

## 6. 残論点（実装前に要判断）

1. **steal の最終形**: 永久剥奪 / 一時奪取（lease_* の下地が既にある）/ どの程度可逆か。
   来歴進化は steal を「進化素材の生産」と位置づけたが、奪取が現物移転か一時かは未確定。
   新規枯渇（3AI 指摘）と緊張感の両立で決める。
2. **昇格条件の数値バランス**: wins/kos 等の閾値、トークンコスト。インフレ/デフレしない調整。
3. **同一 mint メタデータ更新の技術検証**: Solana で単体昇格を mint 不変で実装できるか。
4. **steal タイムアウト攻撃対策**（Gemini 指摘）: reveal 順序の griefing。steal を残すなら必須。
5. **法務確認（最優先・弁護士）**: 「ante 撤廃 + カード奪取 + 市場売買」構成の各法域評価。

## 7. 実装に進めるもの / まだ設計のもの

**すぐ実装可能（来歴進化の骨格）**:
- evolve_cards を「2枚合成」から「単体昇格 + 来歴ゲート」に再設計。
- Common→Uncommon の来歴ゲート（wins ≥ N）を `require!` で追加（最小の第一歩）。
- 既存 CardBattleHistory のフィールドを読むだけ（新規ストレージ不要）。

**まだ設計（§6 を詰めてから）**:
- steal 本体（YKK-44）、トークン経済詳細（YKK-43）、法務確認。

→ 実装の第一歩は「**来歴ゲート付き単体昇格**」を evolve_cards に組み込むこと（steal/トークンと独立に着手できる）。
